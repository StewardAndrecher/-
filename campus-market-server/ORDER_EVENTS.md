# 第73课：订单操作记录与进度时间线

新增 `sql/lesson73-order-events.sql`，没有新增 Maven 依赖。**先停止旧后端**，备份数据库，再执行一次迁移，最后启动新后端。建表和补录是两条 SQL，不能声称整个脚本是一个原子事务；若补录失败，保持后端停止，排查并完成补录后再启动，勿重复建表。

## 写入规则

订单创建、模拟付款、卖家交付、买家收货、买家取消、系统超时关闭均在原业务事务中调用 OrderRepository.append。记录失败使订单状态、商品状态/版本和记录一起回滚；商品缓存仍在事务提交后失效。锁顺序仍为商品→订单，重复请求在追加前返回，不重复记录。订单内序号1..4，主键和操作唯一约束作为最后防线。

操作人来自服务端当前登录用户，昵称在操作时保存；订单双方昵称仍是下单快照。超时无论被定时任务还是付款/取消请求触发，均记 SYSTEM（超时规则），不假称买家主动关闭。事件时间取对应数据库订单时间字段，记录时间也由数据库生成。请求中不能指定操作人或时间。

历史订单仅补一条 HISTORY_SNAPSHOT，保存迁移时状态、SYSTEM、迁移时刻，不能据已有里程碑重建实际操作人/完整历史。后续合法状态变化接着追加。

这是**应用层只追加**的操作记录：没有事件修改/删除接口；数据库管理员能修改，删除订单会级联删除事件，不能称为不可篡改审计、合规存证或真实支付流水。当前订单最多四步，未来退款/售后必须重新设计事件类型和数量限制。

## 读取

`GET /api/orders/{id}/timeline`，Authorization Bearer，返回 `{order, events}`。仅买家或卖家可读，不存在及非参与者均404，未登录401，非法id400。`Cache-Control: no-store`。只读 REPEATABLE_READ 事务使订单和记录属于同一数据库快照；读取不会自动关闭超时订单。旧详情和列表响应保持兼容。

事件字段：sequence/action/fromStatus/toStatus/actorRole/actorId/actorNickname/occurredAt/recordedAt。没有密码、令牌或网络地址。

## 验证方法

OrderTimelineIntegrationTest 使用独立数据库和独立 Redis，验证四步/取消/系统超时、历史快照继续推进、权限、幂等并发、回滚、事件插入失败时原状态回滚，以及一致快照。真实库升级只新增表，不创建测试交易。页面完整流程在隔离库验收。
