# 第95课：本页通知批量已读

新增软件包0，数据库迁移0。复用现有会话、通知表、Spring JDBC事务与uni-app模态确认。通知页新增“本页未读标为已读（N条）”，确认后只提交当前页已显示的未读通知编号，不提供跨页“全部已读”。

## 接口与事务

POST /api/notifications/read-batch，Authorization沿用当前登录会话。

```json
{"ids":[9,7]}
```

ids必须是1至20个不重复的JSON整数，范围1～9007199254740991。字符串、小数、布尔、null、越界及重复编号均400。严格反序列化避免把1.5或字符串"1"默默转换为合法编号。接口没有用户编号参数，管理员也不能绕过收件人检查。

事务先查询并锁定当前用户的全部指定通知；数量不匹配时返回404，整批不修改。更新通过COALESCE(read_at,CURRENT_TIMESTAMP(6))保留首次已读时间；更新失败整批回滚。响应records按id升序返回这些通知的权威已读状态，成功no-store；未登录401。输入顺序不影响语义。使用参数占位符构造IN条件，动态部分仅为服务器按已校验数量生成的问号。

重复请求和与单条已读并用不会重置首次时间。交叉批量按编号排序查询，事务保护一致性；这不承诺任何并发组合都永不死锁，事务错误应先刷新核对，幂等接口允许用户显式重试。单次最多20条限制锁范围和响应体规模。

## 为什么只提交明确编号

页面展示9、7两条未读，用户打开确认框时收到新通知11。请求仍是ids=[9,7]，11保持未读。不能根据点击时的当前时间、最大通知ID或“当前账号全部未读”扩大更新范围。其他页的通知也不受影响。

前端在弹窗出现前复制未读项及内容快照，用户确认后才发POST。弹窗期间和请求期间禁止重复批量、详情打开、刷新与筛选，避免同一页面并发操作混淆。取消不写接口、不清除原页面。账号/Token改变、隐藏或卸载会使旧回调失效，确认阶段失效不再发请求；请求已发出时可能已在服务器提交，但旧结果不会更新新账号页面。

收到成功回执后，逐项核对编号集合、正文与目标信息一致，且每条readAt非空。不能只凭HTTP200就猜测成功。通过后清除旧列表和数量，回到第一页重新读取列表及未读数；未读筛选最后一页被读空时也不会停留在越界页。刷新后的新通知仍可以显示为未读。

请求超时或回执异常时结果未知，清除旧数据并要求刷新；不自动重发，不把未读数直接减N。刷新后可以再次显式标记仍未读的通知，后端天然幂等。列表和总未读数仍为独立请求，不是跨请求原子快照。
